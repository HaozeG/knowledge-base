# KV-Cache Optimization for LLM Inference — PagedAttention, Prefix Caching, and Compression

## Overview

Every token generated by a transformer decoder requires attention over all preceding tokens. Caching the Key (K) and Value (V) tensors for previously processed tokens avoids recomputing them — this is the KV-cache, and it is the dominant memory consumer in LLM inference. For a 70B model with 128K-token context at BF16, the KV-cache can exceed 640 GB — 3–8× the model weights. KV-cache management determines how many concurrent requests a GPU can serve, what context lengths are feasible, and whether inference is compute-bound or memory-bound.

- [supported][src:pagedattention-vllm-2025] PagedAttention (vLLM, SOSP 2023) partitions the KV-cache into fixed-size blocks stored in non-contiguous physical memory, analogous to virtual memory paging. This eliminates 60–80% of the memory waste caused by fragmentation and over-reservation in traditional contiguous allocation: instead of pre-allocating the maximum possible KV-cache per request (wasting memory for short sequences), vLLM allocates blocks on demand and reuses freed blocks across requests. The result is 2–4× higher request throughput at equivalent GPU memory.
- [supported][src:sglang-radix-attention-2025] SGLang's RadixAttention uses a radix tree data structure for prefix-aware KV-cache sharing: requests with common prompt prefixes (e.g., system prompts, few-shot examples) share the same KV-cache blocks. Combined with cache-aware load balancing (routing requests with the same prefix to the same GPU), this achieves up to 1.9× throughput improvement for workloads with high prefix overlap (chatbots, RAG applications).
- [inference] The KV-cache is the memory bottleneck that makes inference memory-bound at high batch sizes. For a Llama-3-70B model serving 32 concurrent requests with 4K-token contexts: KV-cache = 32 × 4,096 × (2 × 80 layers × 8 heads × 128 head_dim) × 2 bytes ≈ 130 GB. Model weights = ~140 GB. Total HBM = ~270 GB — exceeding A100's 80 GB but fitting on H100's 141 GB. Every doubling of context length or batch size doubles the KV-cache pressure.

## Architecture-Level Solutions

### Grouped-Query Attention (GQA) and Multi-Query Attention (MQA)

- [inference] MQA uses a single K/V head shared across all query heads, reducing KV-cache size by the number of query heads (typically 8–32× reduction). GQA generalizes this: G groups of query heads share one K/V head each, providing a smooth trade-off between MQA's memory efficiency and standard MHA's model quality. Llama 3, Mistral, and Gemma all use GQA with G=8, achieving ~8× KV-cache reduction vs. MHA.
- [inference] GQA/MQA are post-training architecture changes: existing MHA models can be "uptrained" to GQA with 5–10% of the original training compute, preserving >95% of model quality. This makes GQA the most impactful single optimization for inference memory — it requires no runtime changes and no accuracy trade-off.

### PagedAttention and Block-Level Management

- [supported][src:kv-cache-optimization-uplatz-2025] PagedAttention's block-level management enables three key capabilities: (1) **continuous batching** — dynamically adding and removing requests from a running batch without rebuilding the KV-cache; (2) **prefix caching** — requests sharing a common prompt prefix share physical KV-cache blocks; (3) **KV-cache offloading** — swapping cold blocks to CPU memory and prefetching them back when needed. The block size is typically 16 tokens, providing a balance between allocation granularity and metadata overhead.
- [inference] The block-level approach is a general memory management pattern that can be applied beyond attention: activation checkpoints, optimizer states, and gradient buffers can all benefit from page-based allocation. TensorRT-LLM and TGI have adopted similar approaches, making block-level KV-cache management the de facto standard for production inference.

### KV-Cache Quantization and Eviction

- [inference] KV-cache quantization compresses K and V tensors to 4-bit or 2-bit precision, reducing memory footprint by 4–8× at the cost of slightly higher attention error. KIVI and KVQuant (2024–2025) demonstrate that key tensors are more quantization-sensitive than value tensors — K's structured patterns (positional encoding, attention patterns) degrade more under quantization than V's smoother distributions. Asymmetric per-channel quantization preserves K accuracy better than symmetric per-tensor quantization.
- [inference] KV-cache eviction discards tokens that contribute least to future attention, keeping the cache within a fixed budget. PagedEviction (2025) performs structured block-wise pruning: whole KV-cache blocks are evicted based on estimated future importance, integrating directly with vLLM's block management. The challenge: eviction decisions must be made online (you don't know which tokens future queries will attend to) and must not cause catastrophic forgetting (discarding critical tokens that break coherence).

## Open Questions

- OPEN: Can KV-cache quantization to 2-bit achieve production-quality accuracy for all model architectures, or is 4-bit the practical floor given the structured noise in attention keys?
- OPEN: As context lengths extend to 1M+ tokens (Gemini 2.5 Pro), does the KV-cache become the dominant cost in the entire inference pipeline, making attention mechanism redesign (linear attention, state-space models) the only scalable long-term solution?
- VERIFY: RadixAttention's 1.9× throughput improvement is for high prefix-overlap workloads — improvement for workloads with low prefix overlap (unique prompts per request) may be negligible.
